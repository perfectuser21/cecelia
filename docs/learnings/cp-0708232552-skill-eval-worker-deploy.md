## skill-eval-worker 超时回收 + pm2 常驻脚本 + 并发冒烟（2026-07-08）

### 根本原因
`skill-eval-worker.js` 原实现只支持"手动跑一次"，缺三样东西才能真正常驻：① worker 崩溃/被杀后卡在 `status='running'` 无法自愈的回收机制；② `runOnce()` 跑完即退出，不能直接被 pm2 当常驻进程管理，需要一层 wrapper 循环；③ `claimPendingTask()` 的原子互斥语义只有 mock 单测覆盖，没有针对真实 Postgres 的验证脚本。

过程中发现的两个值得记录的坑：
1. 冒烟脚本 fixture 若把 `task_id` 留 NULL，`claimPendingTask()` 的 `UPDATE ... WHERE task_id = (子查询)` 在 SQL 语义上 `NULL = NULL` 恒为 `UNKNOWN`，会导致冒烟脚本产生假 FAIL——不是被测代码有 bug，是诊断脚本自己的 fixture 设计不符合真实数据形状（生产路径的 `task_id` 从不为空）。
2. `reapStaleRunning()` 的设计初衷是给"常驻多实例部署"兜底，但如果真的扩展到多实例，且某个任务合法处理耗时超过回收阈值，会被另一个实例误判为卡死、重置回 pending 后被重复认领——这个函数目前只在单实例部署下安全，多实例扩展前必须先给处理中任务加心跳刷新 `updated_at`。

### 下次预防
- [ ] 写任何"验证并发/原子性"的诊断脚本时，fixture 数据必须复刻生产路径的真实数据形状（非空外键、非空约束等），不能图省事留空字段——留空可能恰好绕过被测逻辑依赖的语义，产生假阴性/假阳性。
- [ ] 任何带"超时回收/看门狗"语义的函数，如果注释或设计文档提到"支持多实例"，必须显式检查：回收动作是否会误伤"仍在合法处理中"的任务；没有心跳/续约机制的回收器默认只对单实例安全，要么补心跳、要么把限制写进 JSDoc。
- [ ] 设计文档里承诺的"可通过 env 配置"的参数，实现时要真的接 `process.env`，不能只把默认值写死在函数签名里——review 阶段可以用"逐条对照设计文档与 diff"的方式抓出这类"看似做了、实际没接线"的偏差。
