## 已验证历史业务方法恢复（2026-10-13）

### 根本原因

原控制器恢复只继承上一运行的合同和定义，具备同版本重试，但没有历史业务成功资格、隔离方法安装与原目标独立验收，因此不能称为版本回退。发布CI、执行span或执行者自述不能替代精确历史业务PASS和官方独立核验。

### 下次预防

- [x] 候选按同Workflow固定身份与严格兼容合同筛选；旧方法的安全shell字节不得替换当前底座。
- [x] 准备和启动分别检查两个当前部署及历史资格；准备后证据失效必须在SSH、资源锁和租约前拒绝。
- [x] 新run绑定所选方法和组合摘要，原目标、输入与总预算保持；最终需完整执行路径及原目标/方法双定义独立验收。
- [x] 无候选明确记录拒绝原因，同版本重试不冒称已验证旧版恢复；旧失败产物与运行结果保持原样。

- [x] 旧run核验只要求当前可读的副作用证据与正式runner隔离约束，不能把未授权未来目录的存在当作恢复前置；新run目录隔离留在业务启动前机械检查。

### 聚合发布的安全归属
- 根因：将整包components当监督器依赖，会把同release当前业务代码一并锁死，历史不同方法字节无法选中。
- 防护：只从唯一meta workflow冻结活动闭包取安全依赖；七个不同workflow聚合的真实PG正反例永久覆盖。首版业务skill依赖无法机械证明，筛选与起跑统一拒绝，不能等运行端才发现不支持。
- 纯code业务活动的执行类型不是安全职责；按明确preflight/cleanup/controller及meta真实闭包守住安全边界，保留不同业务字节的PG反例。
