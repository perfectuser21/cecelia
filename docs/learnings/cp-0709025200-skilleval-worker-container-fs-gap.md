## skill-eval-worker 修复容器/宿主机文件系统隔离阻断（2026-07-09）

### 根本原因
Brain 跑在 Docker 容器（`cecelia-node-brain`）里，`POST /api/skill-eval/upload` 把上传的 zip 落盘在**容器内**的 `SKILL_EVAL_STAGING_DIR`；常驻评估 worker（`skill-eval-worker.js`，pm2 拉起）跑在**宿主机**，直接对同一个路径 `fs.readFile` 时报 ENOENT——容器和宿主机是两套独立文件系统，路径字符串相同不代表指向同一份文件。

这个问题在"部署完成"验收时完全没被发现：验收只检查了 pm2 daemon 是否 online、HK nginx 反代是否连通，都是进程/网络层面的检查，从未真实走过一次"上传→worker认领→处理"的完整数据流。直到本次真实上传测试 zip 才暴露——worker 拿到任务后立即因为读不到文件而失败。

### 下次预防
- [ ] **验证"部署完成"时，必须包含一次真实数据流打通，不能只验证进程存活/网络联通**。尤其是涉及"生产者在容器里、消费者在宿主机（或反过来）"这种拓扑时，双方以为共享的文件系统/路径极可能其实不共享——这类问题只有真实跑一次数据穿越两端才能发现，mock 测试和进程健康检查都测不出来。
- [ ] 设计跨进程边界（尤其跨容器/宿主机边界）传递大对象（文件、zip）时，优先假设"文件系统不共享"，默认走显式的数据传输通道（HTTP API 拉取内容 / 消息队列携带内容 / 对象存储），而不是约定一个"共享路径"——除非确认过 volume mount 真的配置了。
- [ ] 本次选择"worker 改走 HTTP 拉取 zip 内容"而非"给容器挂共享 volume"，是因为后者要改 Docker/部署配置（风险更高、需要重启容器）；前者是纯应用层改动，不涉及生产容器配置变更。以后遇到类似"两端环境隔离"问题，优先evaluate"改应用层代码"是否能绕开"改基础设施配置"，risk 更低。
