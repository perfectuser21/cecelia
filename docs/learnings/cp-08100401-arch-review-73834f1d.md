# 架构巡检 Learning

## 04:01 UTC 架构巡检（2026-08-10）

### 根本原因

- 生命周期“写了时间”与“时间语义正确”是两层合同。PR #4754 补了状态迁移写入，但没有迁移无时区字段；DB 连接仍在 America/Chicago，当前任务继续出现约 13 小时表面偏差。
- hard-off 只挂在旧 tick 入口，新拆出的 scheduler-jobs、projection 与 PromotionJob 直接由 server 启动；主 scheduler stopped 不能证明环境没有调度副作用。
- Gate3 与 Auto Staging 能诚实报红，但报红后没有唯一恢复所有者。生产通过 CI 之外路径追上，staging 仍落后一版，部署结果形成多本账。
- review runner 的 lock、executor kind、payload run id 与 callback CAS 分散写入；当前执行再次只写前两项，重启后重复派发。
- 共享工作区的 `node_modules` 来自 Darwin，Linux arm64 巡检直接运行 Vitest 会缺原生 Rollup/Esbuild；只有注入同版本平台包后才真实收集测试。
- 实时语音功能在三个目录复制完整状态机，其中两份逐字相同；目录分层没有形成唯一实现边界。

### 下次预防

- 时间修复验收同时断言列类型、DB timezone、Node 序列化与跨时区真实记录，不以“字段非空”收尾。
- 环境级关闭能力必须枚举所有 interval/loop，并以日志、进程和 DB 零写入三层取证。
- 部署巡检分别记录 Gate3 裁决、production SHA、staging SHA 与失败后的恢复路径，不能用最终 runtime 反推 CI 成功。
- 异步 runner 用同一 task 证明 claim、lock、run-id、heartbeat、recovery 投影和 callback CAS 共享同一身份。
- 测试输出必须包含真实收集文件数/用例数；原生依赖平台不匹配时使用任务局部依赖，不修改共享 `node_modules`。
- 发现三份同类状态机时，先用 hash/行数证明复制，再登记唯一正本收敛任务。
