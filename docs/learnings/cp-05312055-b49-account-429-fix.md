# B49 — account-rotation 429 降级死循环

## 根本原因

`fetchUsageFromAPI` 把 usage API 的 429（账号超配额）和普通失败（超时/500）一视同仁返回 null。
`getAccountUsage` 收到 null 后降级到 `getStaleCached`（返回最后一条缓存行，不管多旧），
旧缓存显示账号健康（如 5h=4%），导致 `selectBestAccount` 反复选中已超配额的死账号，
账号再次 429 → 死循环，永远不切到健康账号。

实证：account1 配额耗尽返回 429，pipeline 反复派 GAN reviewer 到 account1，
每次 3 秒失败（"Usage credits are required for long context requests"，input_tokens=0），
任务卡死。手动 cap account1 后才切到 account2 正常跑通。

## 下次预防

- [ ] usage API 返回 429 必须判账号不可用，不能降级到乐观旧缓存
- [ ] 区分"账号真超配额"（429，硬淘汰）vs"端点瞬时抖动"（超时/500，可降级旧缓存）
- [ ] 账号选择的淘汰维度要完整：不只看缓存的百分比，还要尊重实时 429 信号

## 修复

`packages/brain/src/account-usage.js`：
1. `fetchUsageFromAPI`：429 → 返回 `{ __rateLimited: true }` sentinel（非 429 仍返回 null）
2. `getAccountUsage`：收到 sentinel → 标记 `five_hour_pct=100`（≥ USAGE_THRESHOLD 80）→ 被 `isAccountEligibleForTier` 淘汰 → 自动切健康账号
