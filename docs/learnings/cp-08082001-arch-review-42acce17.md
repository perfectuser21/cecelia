# Learning：局部 freshness 与身份校验全绿，不代表组合合同闭合

本轮新增问题都不是单个函数明显报错：line ledger 生产端每天正常产出、arch review 消费端也能正确查询最近 20 小时，但 24 小时周期与 20 小时窗口组合后，每天固定出现约 4 小时零上下文；Kernel 的 CI 与 PR 分支修复也分别通过了定向单测，却在枚举和身份边界上引入新的 fail-open。

### 根本原因

- 时间窗口只在各模块内部验证，没有用真实调度时点做跨模块时序测试。
- 为解除一次死循环，消费端把上游不一致压缩成宽松判定：非 `BLOCKED` 即可视为 pass，task short-id 可替代精确签发分支。
- “能继续跑”被优先于“真相可证明”，UNKNOWN 与双正本因此进入正常路径。

### 下次预防

- [ ] freshness 合同必须同时声明生产周期、消费窗口和容差，并测试完整 24 小时时间矩阵。
- [ ] 外部枚举必须逐值映射；UNKNOWN/null 一律保守，不允许用 `!= bad` 推导 good。
- [ ] 已有服务端签发身份时，兼容逻辑不得退化成可猜测子串；先统一身份派生，再收紧校验。
- [ ] 架构巡检的回归集加入跨模块组合场景，不以局部单测数量代替端到端不变量。
