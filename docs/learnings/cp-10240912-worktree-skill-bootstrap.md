# 新工作区必须具备与CI相同的固定来源依赖

## 根本原因

真实A8任务的README实现通过三项内容断言，但本地registry-lint报25个缺失技能路径。CI在该检查前恢复.skills-source.json固定来源，runner却只安装npm依赖。自动预检修复模型误把缺少的依赖当坏登记，将5份YAML的25处入口置null，最终被范围验收拒绝。失败样本不重试、不追认。

## 下次预防

- [x] 新工作区在启动模型前通过现有脚本恢复和校验固定Skill来源，失败作为准备错误停止，不把来源缺失交给模型修登记。
- [x] 跳过npm安装不等于跳过其它固定来源依赖；预检环境要对齐CI的前置准备。

## 验证

测试先3 RED/1 PASS，修后4 PASS；相关runner/deps/lease共41 PASS。独立修复工作树真实调用runner准备：registry原25 FAIL，经固定来源install+verify后0 FAIL，原登记YAML字节未改。正常正式CI及后续两条新任务实跑分别验收；本修复不代表样本已通过。

原基线锁文件被实时审计检出body-parser/multer/zod高危，固定更新而非豁免；OpenAI旧SDK的Zod3可选peer限制导致残留，用支持Zod4的6.49和正式monorepo根锁文件解决。实际新依赖安装后，SDK与应用真实执行、只替换HTTP传输，验证POST参数、float向量和429 quota错误；真实网络调用0。新增33项相关回归通过（含前述4项重叠），原运行审计脚本通过，现有白名单未改。

来源门在候选23e仅拒绝额外更新的嵌套Brain锁文件，该文件并非本次正式monorepo安装需要的更新；撤回该多余变更，保留原失败来源报告，继续按新最终HEAD正常验收，不增加来源角色或豁免。
