# Learning：闹钟总账——"另起一本账"的冲动要先查现成表

### 根本原因
- 盘点出 417 个定时任务散在 9 种机制里无人统管，第一反应是再建一张"总账表"。实际上仓库里已经有半个总账：`ops_schedule_entries`（433，每 5 分钟采、有来源心跳、推 Notion），缺的只是几列和两条自动写入腿。再建新表等于第四棵树。
- 新列一旦由"采集腿 / Brain 每分钟 / 导入脚本 / 人"四方共写，最容易出的事是机器 upsert 冲掉人的结论（归属、备注、挂树）。所以 SET 子句必须只含机器列，且要有真 PG 测试证明。
- 盘点里的逻辑名（"opc-okr-sync.py（5 条 cron 行）"）和采集腿 label（"脚本 @ cron"）并不一一对应，按名字精确匹配会把 58 条采集行留成"未登记"。

### 下次预防
- [ ] 新增"总账/注册表"类需求，先 `git grep` 现有 `ops_*`/`*_registry` 表，能加列就不建表。
- [ ] 多方共写的表：机器列/人工列分区写进迁移注释，并配「SET 子句不含人工列」的单测 + 真 PG 的"人写后机器刷新仍保留"用例，亲手变异一次看它报红。
- [ ] 每分钟写的行必带降噪 WHERE（沿用 ops_workflows 同款条件），否则会把 Notion 推送的 LIMIT 吃光。
- [ ] 导入脚本先干跑（API 缺省 dry_run），未匹配/未解析的如实列出，不猜。
