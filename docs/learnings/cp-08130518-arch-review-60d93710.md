# Learning：局部环境守卫与 migration 版本号都不是系统级权威

本轮 #4853 的 `BRAIN_PREVIEW` 守卫在代码和运行日志中都正确生效，但只控制 scheduler/projection。克隆 DB 的 `tick_enabled=true` 仍启动主 Tick，Nightly 仍运行，两个 Preview 因而同时执行同一任务。局部函数测试证明“这个入口不启动”，不能证明整个实例零副作用。

production 又写入 CLOSED 未合并 PR 的 migration 413/414；OPEN #4860 随后复用 413 表达另一种 schema。由于 ledger 只按编号去重，Preview 将未执行的新迁移当成已应用，预期列真实缺失。最大版本号、同号记录或测试绿色都不能证明迁移内容一致。

### 根本原因

- 环境生命周期分散在主 Tick、Nightly、scheduler、projection、promotion 与 executor 多个入口，没有一个实例级 fail-closed 总闸。
- Preview 克隆运行态数据，却只终止部分 task type，没有把 working_memory 和可派发任务视为燃料。
- migration 权威只比较序号，不绑定已合并 commit、描述、内容 hash 与目标数据库；非 main 执行路径可以写 production ledger。
- 文件锁按 task UUID 覆盖写入，没有 environment/run 身份与原子独占语义。
