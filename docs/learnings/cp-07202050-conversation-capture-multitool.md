## 对话捕获多工具扩展——session闲置判定+Haiku摘要（2026-07-20）

在 PR #4135（对话原始捕获，Claude Code 专属，逐条消息轮询）上线后，Alex 用了一下觉得应该"以 session 为单位"、"session 结束才有意义"、"要能看到 topic 总结"，且要求支持 Codex/Grok（多工具场景下 Stop Hook 是 Claude Code 专属，不能靠 hook 判定会话结束）。调研发现 Codex（`~/.codex*/history.jsonl`）和 Grok（`~/.grok/sessions/*/prompt_history.jsonl`）都已有官方的"纯人类输入"专用日志，比 Claude Code 自己的完整 transcript 更省事，不需要重新过滤 tool_result/assistant 内容。

设计上采用"按 session_id 分组 + 15 分钟无新消息判定闲置"作为跨工具通用的会话结束判定，天然不依赖 hook；dedupeKey 绑定 `source:sessionId:lastEntryId` 而非只绑 `sessionId`，确保同一 session 复聊后再次闲置能产生新 capture，不会漏内容。

### 根本原因（最后一轮综合代码审查抓出的 2 个 Critical）

1. **mtime 增量扫描窗口与闲置判定阈值在时间常数上互斥**：三个 Task 各自独立开发、各自审查都通过，但组合起来后，"用滑动的'上次扫描时间'作为 mtime 下限"（Task1 沿用 PR#4135 的性能优化手段）和"要等 15 分钟无新消息才判定闲置"（Task2 新引入）这两个设计放在一起，数学上必然导致文件在真正闲置够 15 分钟之前就已经被 mtime 过滤器永久排除——扫描间隔（10min）小于闲置阈值（15min）时，不存在同时满足"文件够新鲜"和"session 够闲置"的窗口。所有单测/集成测试都用 `sinceMs=0` 或每次重置 sentinel（等价于每次都是冷启动），系统性地看不见这个只有在"哨兵已存在 + 连续多轮真实时间流逝的扫描"场景下才会暴露的 bug。
2. **配套的次生问题**：修复 #1（放宽扫描窗口）之后，如果不加"是否已捕获"的前置检查，同一个 session 会在扩大的重扫窗口内被反复喂给 LLM 做摘要，造成重复计费——这个问题在只看 Task2 单独实现时不存在（当时窗口很窄，session 基本不会被扫描第二次），是 Critical #1 修复后才会被放大暴露的组合问题。

### 下次预防
- [ ] 跨模块的"时间常数"（扫描间隔、闲置阈值、缓存 TTL 等）如果彼此之间有隐含的大小关系依赖，必须在设计阶段显式写一条不变量断言或注释（比如"必须保证 LOOKBACK_WINDOW > IDLE_THRESHOLD"），不能指望测试覆盖到——本次这个 bug 潜伏在 3 个独立 Task 的接缝处，任何单个 Task 的测试都测不出来，只有对整个分支做"跨任务组合"审查的最后一轮才抓到
- [ ] 涉及"周期性重新扫描同一批数据"的设计，一旦引入外部付费调用（LLM/第三方API），必须同时设计"是否已处理过"的前置检查，不能假设"重扫不常发生"就不用防——扩大扫描窗口（为了修一个 bug）反而可能意外放大另一个本来隐藏很浅的问题
- [ ] 测试如果全部依赖"重置状态=冷启动"的写法（`afterEach` 清空 sentinel、传 `sinceMs=0`），要专门补至少一条"真实多轮扫描、状态不重置、时间真实流逝"的集成测试，否则这类"跨扫描周期"的 bug 永远测不出来
