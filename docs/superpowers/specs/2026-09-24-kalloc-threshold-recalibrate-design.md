## 1. 问题

`check_kalloc_guard` 的三档阈值是 2026-09-18 那次事故（`data.kalloc.1024` 涨到 12.7GB、
kernel_task 91% CPU 机器卡死）后按**当时的内存余量**定的：

| 档 | 阈值 | 动作 |
|---|---|---|
| WARN | 4G | 仅记日志 |
| ALERT | 8G | 报 Brain P1 |
| CRITICAL | 11G | 凌晨 3-5 点自动重启；非安全时段报 P0 |

2026-09-24 实测，这组阈值已经不匹配现实：

```
kalloc.1024 = 5.50G      ← 未达 8G 告警线，按设计只记日志
但同一时刻：
  空闲内存 188M ｜ swap 3977M/5120M ｜ load average 5.3
  janitor 自己每 15 分钟记一次「内存高压 99%」
```

**余量被其余占用吃掉了**：8 个 Claude Code 会话 2.84G + 11 个 tmux + 14 个 mosh-server
+ OrbStack VM（本次已从 5120 调到 2048 MiB）。同样的 kalloc 数字，今天比 9-18 疼得多。

**告警线落在「快死了」，不是「开始疼」。**

## 2. 增长速率（取自现有数据，非新建采集）

`/tmp/janitor-frequent.log` 已有 138 个样本（哨兵每 15 分钟记一次）：

```
2026-09-22   4.00G → 4.76G   (69 样本)
2026-09-23   4.77G → 5.50G   (69 样本)   +0.74G
```

**稳定 +0.75G/天。** 按现行阈值推算：8G 约 9-27 触发告警，11G 约 10-01 触发自动重启。

> 本次**不新建任何采集**。要建追踪器的念头在开工前被 GitHub 撞车检查挡下——
> PR #5400 早已把哨兵并入 janitor，且决策 `64d38870` 明确否决过独立哨兵。

## 3. 改什么

**只动数字，动作与结构一概不动。**

| 档 | 现行 | 新 |
|---|---|---|
| WARN | `4*1024*1024` | `3*1024*1024` |
| ALERT | `8*1024*1024` | `5*1024*1024` |
| CRITICAL | `11*1024*1024` | `7*1024*1024` |

位置：`scripts/ops/janitor.sh` 的 `check_kalloc_guard`（三处 `-ge $((N*1024*1024))` 比较）。

**明确不做**：把 CRITICAL 改成读真实空闲内存而非 kalloc 代理值。更精确，但引入新的失败
模式，而现行这套简单设计是 9-18 验证过的。本刀只动数字。

## 4. 后果

| | |
|---|---|
| 合并当天 | 当前 5.50G ≥ 新 ALERT 线 5G → **立即触发一次 Brain P1 告警**。这是预期行为不是误报 |
| 自动重启节奏 | 11G÷0.75 ≈ **14 天** → 7G÷0.75 ≈ **9 天** |
| 代价 | 凌晨 3-5 点的无人值守重启更频繁 |
| 收益 | 不再攒到 188M 空闲 + 4G swap 才动 |

## 6. 测试策略

**档位：unit（纯 shell 行为断言）。** 无 E2E、无 integration、无新增 smoke——
本改动只动三个数字，既有测试已用 `KALLOC_KB`/`KALLOC_HOUR` 注入做逐档**行为**断言
（不是词语断言），改阈值同步改注入值即可。

### 注入值必须落在新区间，且要真能红

`scripts/ops/__tests__/janitor/janitor_kalloc_guard.test.sh` 现有注入值在新阈值下会错档：

| 用例 | 现值 | 新阈值下落到 | 处理 |
|---|---|---|---|
| NORMAL | 10000 KB (0.01G) | 静默 ✓ | 不动 |
| WARN | 5G | **ALERT** ✗ | 改 3.5G |
| ALERT | 8.11G | **CRITICAL** ✗ | 改 6G |
| CRITICAL | 11.44G | CRITICAL ✓ | 改 8G（贴近新线） |

**TDD 成立性推演**（commit-1 改测试后，对着**未改**的 janitor.sh 必须红）：

| 新注入值 | 旧阈值(4/8/11)行为 | 新阈值(3/5/7)期望 | 结果 |
|---|---|---|---|
| 2.9G | 静默 | 静默 | 两边都绿（记录下边界，非失败用例） |
| **3.5G** | 静默 | 「早期预警」 | ✅ **红** |
| **6G** | 「早期预警」 | 「偏高」+ curl | ✅ **红** |
| **8G** | 「偏高」 | 「危险」+ curl | ✅ **红** |

三条真红，不是崩溃红——断言的是输出措辞与是否调用 curl/sudo，不是脚本能否跑通。

### 保留不动的用例

- **八进制炸弹回归**（`hour=08`/`09` 前导零需 `10#` 前缀）：与阈值无关，注入值只需仍落在
  CRITICAL 档即可（8G 满足），断言一字不动。
- **CRITICAL 安全/非安全时段分支**：结构不变，只换注入值。

### 变异测试（手工纪律，CI 无机械闸）

把 janitor.sh 的阈值改回 `4/8/11` → 上述三条必须**断言红**；改回 `3/5/7` → 转绿。
亲眼见红才算数。
