### 1. `schema_version` 表记录与实际状态不一致

```

→ 341 | zenithjoy_schema_move | 2026-07-13 10:19:50（这是最初出事故那次错误执行留下的记录）
```

但实际上：
- 5张裸表（`user`/`session`/`account`/`verification`/`operator_sessions`）**现在还在 `cecelia` 库的 `public` schema**（P0事故回滚时挪回去的，没有重新迁移）

- (b) 或者干脆决定这5张表就留在public，不追求"消除撞名风险"这个目标了，把DoD F2条目直接砍掉

## 生产事故复盘（避免重蹈覆辙，务必读完再动手）

1. **2026-07-13夜间**：Brain tick 自动派发 Task1，在PR未合并/CI未过的情况下**对生产库执行了真实migration**，其中`ALTER DATABASE cecelia SET search_path=zenithjoy,public`是数据库级别全局设置，导致Brain自己的`public.tasks(goal_id)`查询被ZenithJoy同名`zenithjoy.tasks`表抢先解析，Brain生产容器crash-loop
2. 已修复：删除该语句，改成ZenithJoy自己的`pg.Pool`连接级`options:'-c search_path=zenithjoy,public'`；并加了**永久CI守卫**——`packages/brain/src/__tests__/migration-341.test.js`里有个全局扫描测试，任何`packages/brain/migrations/*.sql`文件出现`ALTER DATABASE`直接拦截合并
3. **教训**：headless task在PR未合并时不应该对共享生产数据库执行真实DDL；任何跨App共享物理库的场景禁止用数据库级别的`ALTER DATABASE`/全局search_path，必须用连接级别或显式schema前缀
