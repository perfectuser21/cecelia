### R-1
针对: S-3, Q-3, I-3
严重度: 阻断
场景: 编写者在原有 `--json` 命令中插入一个字符使它无法执行，随后加入正确的新小节；QA 的原字节有序子序列断言仍通过，读者却看到被破坏的旧命令。
依据: S-3、Q-3 规定将固定基线 README 的每个原字节按顺序作为最终 README 的子序列；该算法允许在任意原字符之间插入内容。现有 `runner/README.md` 有 `status.mjs [--log-dir <dir>] [--json]` 等原命令，I-3 要求原文逐字保留、只允许插入新小节。
说明: 将验收收紧为原有段落、表格和代码块逐字保持，只在明确的新小节边界允许插入；Q-3 用会失败的断言检查原命令未被拆开或插入字符。

### R-2
针对: S-4, S-5, Q-4, I-4
严重度: 阻断
场景: 编写者先提交一版修改 `new-task.mjs`，再提交撤销该修改，最终 HEAD 只比基线多 README；QA 执行 Q-4 列出的命令只能看到两次提交的哈希与最终路径差异，不能据此发现曾经越界修改程序，却可能判范围通过。
依据: S-4 的 verify 命令和 Q-4 的 QA 命令使用 `git rev-list --parents` 列提交、`git diff --name-status <base> HEAD` 列最终差异；前者不显示每个提交改了哪些路径，后者会抹去先改后撤销的路径。I-4 明确要求完整 DAG、逐提交归属及先改后 revert 拒绝。
说明: 在发布前 verify 与发布后 Q-4 分别加入可执行的逐提交、逐父路径及内容/模式检查，覆盖合并提交；保留固定 initial base 和当前全仓清单。过去 verify 现场只凭当时原生记录与外层核验，不要求后续 QA 重造。
