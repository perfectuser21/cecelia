SPEC_PATH 文件格式要求：
- 以 frontmatter 开头，三个键各占一行，写法如下（upstream 为单行 JSON 数组，必须列出 INTENT_IDS 中的全部 I-n，每项形如 `01-intent.md#I-1`）：

- 正文每条规格用标题行 `### S-n`（n 从 1 递增）。每条必须写明：对应的 I-n、要改哪些文件（路径）、怎么验证（具体命令或断言）。
- 每个 I-n 至少被一条 S-n 覆盖。
- 规格之后必须有 `## QA 场景` 小节：代码写完后，一个像真人一样的 QA 会在真实环境里（真起服务、真调接口、真开页面、真跑命令行）按这些场景黑盒验收。每个场景一节 `### Q-n`（n 从 1 递增），依次写：
  - `对应:` 覆盖的 I-n（逗号分隔）
  - `前提:` 环境与数据状态（没有可写「无」）
  - `操作:` 真实用户会做的具体操作步骤（调用哪个接口/点哪里/运行什么命令、传什么数据）
  - `期望:` 用户能看到的结果（接口返回、页面上出现的文字、数据库里的记录、生成的文件）
- 只做 I-n 要求的事，不顺手修：读代码时发现的需求之外的存量问题（别的字段的校验、别的调用方的写法等）不要写进规格，写进 `## 未覆盖真实链路` 并注明「建议另立任务」。合同对抗会把超出 I-n 的改动当「偷换需求（扩大）」打回。
- 可由场景创建的业务测试数据应自己造（先建再查、先写再读），不依赖环境中的偶然数据。任务的固定 initial base、当前 HEAD、真实 Git 历史、已发生阶段及可信来源等前提只能只读核实实际事实，不能由 QA 编造、重建历史现场或拿本轮重跑替代；缺事实如实不能验。QA 在哪里验、地址怎么写、改动前基线怎么起，按下方本仓库规矩的「QA 环境」。本仓 QA 环境验不了的任务，按那里的写法如实上交，不要硬写替代测法。
- 每个 I-n 至少被一条 Q-n 覆盖；Q-n 检查该 I-n 在当前 QA 阶段合法、可观察的条件，其它阶段的条件仍在 S-n 保留并明确对应的真实核验责任，不移交给当前 QA 重做。除正常路径外，为本需求内用户真会遇到的出错/边界路径各写场景。
- QA 场景是黑盒操作，不能是单元测试——「运行 vitest/npm test 通过」不算 QA 场景（那是 CI 的事）。
- INVARIANTS_PATH 是系统的铁律清单（每条 `### INV-xxxxxxxx`，主理人拍板过、不能违反的规矩）。读完后在 QA 场景之后写 `## 铁律对照` 小节：
  - 与本改动相关的每条铁律一行：`- INV-xxxxxxxx：S-2、Q-3 覆盖（一句话说明怎么遵守）`；看起来相关但这次确实不涉及的写 `- INV-xxxxxxxx：不适用：理由`。
  - 判断「相关」宁宽勿漏：本改动碰到的模块、流程、机器、数据只要被某条铁律约束，就要列出。
  - 清单里确实没有一条与本改动相关时，写一行 `无相关铁律：理由`（说清本改动的范围为什么不碰这些规矩）。
- **真实调用方**：改动的接口/脚本有外部调用方（设备 agent、OpenClaw、别的服务、前端）时，在对应 S-n 里写明「真实调用方 shape」：调用方实际怎么发请求（方法、路径、header、body 字段、鉴权放在哪），并给出出处（调用方代码路径或抓到的真实请求）。QA 场景按这个 shape 发请求，不能自己编一个更顺手的。
- **第三方**：依赖第三方 API（模型、推送、支付、平台接口）时，至少一条 Q-n 用真 key 真调一次；预览环境调不了的，登记进下面的 `## 未覆盖真实链路`。
- 规格最后必须有 `## 未覆盖真实链路` 小节：逐条列出这次 QA **没法真验**的链路（mock 掉的第三方、预览环境缺的凭据/设备、只验到落库没验到推送等），每条一行写清缺什么、QA 验到哪一步。确实没有就写一行 `无：理由`。这一段会原样放进 PR 正文给主理人看。
- 可选 `## 判定点` 小节：凡是系统要「推断外部真实状态」的地方（部署成没成功、RPA 页面状态、API 返回怎么解读、真机反馈怎么识别），每个一行：`- <判定点名>｜候选: <可选方法>｜所选: <选了哪个>｜依据: <为什么>｜误判后果: <判错了会怎样>`，五项缺一不可。合同通过后会写进 Brain 决策库。没有就不写或写 `无：理由`。
- 对外暴露的改动（接口、命令行、页面）在相关 S-n 里写明**失败语义**（出错时调用方/用户看到什么、能不能重试）和**输入对抗面**（非法、超长、重复、并发的输入会怎样）。

## 验收阶段边界

先按 01 原义区分发布前 verify、当前产品 QA、会话后控制器及终态核验。保留每条 I-n 的全部条件及原发生阶段，不能为了 I/Q 覆盖而把其它阶段的检查复制成当前 Q-n，也不能以阶段分工免除原条件。当前阶段确实不可验的产品条件仍须如实说明并上交，不能编造替代通过。

例如：01 把发布前当时的暂存区、工作区、全仓未跟踪清单交给 verify，发布后 QA 检查当前固定 HEAD 的范围时，Q-n 应核固定 initial base、完整 DAG 及逐提交归属、当前暂存区/工作区和全仓未跟踪范围，并保留原来源与隔离要求；不得另写一个要求 QA 读取过去现场或发布前报告的 Q-n。历史可由固定 Git 核实的事实仍须真实核实；过去非 Git 现场则由当时 verify 的原生命令、完整输出、退出码及独立外层核验承担。当前 HEAD、干净工作区、哈希、metadata、exit0 或过去的 PASS 都不能替代过去现场的证据；该阶段缺证时，对应阶段及终态验收仍不能通过。

产品 QA 只读 01/02 和允许的前轮裁决，不读 03/04 或旧 QA 自述。控制器来源要求由独立来源门核验实际阶段回执、登记调用和精确提交，QA/裁判只收到固定字段事实，不能假设投影含有未提供的历史命令或现场快照。未来的登记、报告完整恢复、提交、合并或清理，也不能要求 QA 在自己会话结束前证明；仍须在实际发生后由对应控制器门和终态验收核实。每个新 HEAD 的真实 QA、裁判、预览和正式 CI 要求保持。
